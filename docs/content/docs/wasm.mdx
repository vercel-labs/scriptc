---
title: "WebAssembly Modules"
---

A WebAssembly module lets a web page or another application call functions written in TypeScript. Use it when you want to run compiled logic, such as a simulation, a parser, or geometry processing, inside a host that owns the user interface. To build a program that runs on its own under a WASI runtime instead, see [WebAssembly (WASI)](/docs/platforms#webassembly-wasi-preview-1).

You build a module in library mode, with `SCRIPTC_TARGET=wasm32-wasi` and `scriptc build --lib --profile`. The result is a WASI Preview 1 reactor: a `.wasm` file with callable exports, named imports for host callbacks, and its own memory. Your application loads the module, supplies its imports, calls its exports, and handles events, scheduling, and rendering.

Module builds need [zig](https://ziglang.org) and the `@scriptc/runtime-wasm32-wasi` runtime pack in your project, at the same version as `scriptc --version`. See [Cross-compile](/docs/platforms#cross-compilation-via-zig).

```console
$ npm install --save-dev @scriptc/runtime-wasm32-wasi@0.3.5
```

## Define the interface

The library profile names the entry module and its public functions. A reachable callback call becomes a synchronous import from the <code>scriptc</code> namespace.

```ts:counter.ts
declare function changed(value: number): void;
let count = 0;
export function step(delta: number): number {
  count += delta;
  changed(count);
  return count;
}
```

```json:counter.json
{
  "profile_format": 1,
  "name": "counter",
  "entry": "counter.ts",
  "emission": "llvm",
  "abi": {
    "prefix": "counter_",
    "init_symbol": "counter_init",
    "sink_register_symbol": "counter_sink",
    "callback_register_symbol": "counter_callback"
  },
  "callbacks": [{ "name": "changed", "params": ["f64"], "returns": "void" }],
  "exports": [{ "export": "step", "symbol": "counter_step", "params": ["f64"], "returns": "f64" }]
}
```

Build the module:

```console
$ SCRIPTC_TARGET=wasm32-wasi scriptc build --lib --profile counter.json -o counter.wasm
```

Without `-o`, the output is `.scriptc/counter.wasm` beside the profile. The compiler API's `compileLibrary()` returns this path in `archivePath`, as it does for native libraries.

The profile uses the same schema as native library builds. <code>sink_register_symbol</code> and <code>callback_register_symbol</code> name native registration functions; a Wasm reactor does not export them. Wasm binds callbacks during instantiation and delivers panics through <code>scriptc.panic</code>.

Set `"optimization": "dev"` in the profile to turn off release optimization. npm dependencies compile automatically, as in executables. Add `"npm_static": ["three"]` to name packages explicitly, like the [`--npm-static`](/docs/dependencies#explicit-package-selection) option. Unsupported code that the module reaches still produces a compiler diagnostic.

## Instantiate and initialize

A browser host needs a WASI Preview 1 adapter as well as the application's callbacks. Browsers do not supply WASI automatically. Inspect <code>WebAssembly.Module.imports(module)</code> to see the exact imports required by your compiled program. Supply real implementations or explicit failures for unsupported operations.

```js:loader.js
export async function loadCounter(url, wasi) {
  const module = await WebAssembly.compileStreaming(fetch(url));
  let api;
  const instance = await WebAssembly.instantiate(module, {
    ...wasi.getImportObject(),
    scriptc: {
      changed(value) {
        console.log(value);
      },
      panic(pointer, length) {
        const bytes = new Uint8Array(api.memory.buffer, pointer, length);
        throw new Error(new TextDecoder().decode(bytes));
      },
    },
  });
  api = instance.exports;
  wasi.initialize(instance);
  api.counter_init();
  return api;
}
```

This loader assumes an adapter with <code>getImportObject()</code> and <code>initialize(instance)</code> methods, as provided by Node's <code>node:wasi</code>. Browser adapters may use different method names. Initialization must first connect the adapter to the instance's exported memory and invoke <code>_initialize</code> once, then call the profile's <code>init_symbol</code>. Do not call a command-style <code>start()</code>; reactors have no <code>_start</code> export.

After initialization, <code>counter_step(2)</code> returns <code>2</code>, and another call returns <code>4</code>. Calling <code>counter_init()</code> again resets application globals and reevaluates module initialization. Instantiate the module again for independent state and memory.

The native library rules about directions still apply: u8/u32/i32 are export parameters and callback scalars; i64/u64 are export-only. Callback results must be scalars or void. Callback string/byte parameters are borrowed only for the duration of that callback; copy them before retaining them in the host. A <code>cstring</code> callback parameter is one i32 pointer to NUL-terminated text, borrowed the same way; a value containing U+0000 traps with <code>SC4015</code>. The <code>cstring</code> class requires <code>"profile_format": 2</code>. In native libraries it is a <code>const char *</code> with the same rules.

Allocate host input buffers and output slots with <code>scriptc_alloc(size)</code>; a zero result indicates allocation failure. Release each allocation exactly once with <code>scriptc_free(pointer)</code>. Only free pointers returned by <code>scriptc_alloc</code>. These allocations remain live across application calls, initialization, and collection until freed.

Result buffers belong to the module. If the profile declares <code>abi.result_reset_symbol</code>, results accumulate until that function is called. Otherwise, the next application export resets the result arena. Initialization and the optional <code>abi.collect_symbol</code> also invalidate results. Allocation and free do not reset the arena. Copy a result into host-owned storage before invalidating it; never pass its pointer to <code>scriptc_free</code>.

Recreate typed arrays and DataViews from <code>memory.buffer</code> after every Wasm call that may allocate. Memory growth replaces the backing buffer and invalidates older views. Pointers remain offsets into the instance's memory; never use a pointer with another instance.

## Errors and scheduling

A compiled trap or escaped exception calls <code>scriptc.panic(pointer, length)</code> with the native library's structured diagnostic bytes, then traps if the callback returns. Discard the instance after a panic, a Wasm trap, or an exception escaping a host import. Recovery uses a new instance; calling the initialization export does not repair a failed instance.

Host callbacks run synchronously. They must return before calling any application export, initialization, collection, allocation, or free on the same instance. Reentry is rejected. Copy callback data and schedule subsequent work after the outer call returns. The web app can call a frame export from <code>requestAnimationFrame</code> and render its results through Canvas, WebGL, or WebGPU.

See [Limitations](/docs/limitations#browser-embedding) for browser graphics and library-mode restrictions.
