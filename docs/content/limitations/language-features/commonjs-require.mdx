- **CommonJS `require`:** Literal `require()` calls of compiled modules, supported builtins, and JSON documents compile.
  Reading a top-level `const` or `let` require binding before its `require` runs throws the same `ReferenceError` as Node.js.
  A `var` binding that code above its `require` can reach is unsupported, and so is a read that compiles to no checkable expression, such as exporting the binding before the `require`.
  A `require()` of a relative path that names no file when the program is built throws the same `MODULE_NOT_FOUND` error as Node.js, where the call runs.
  The error has Node's `code` and `message` and no `requireStack` property.
  JSON documents are parsed at build time, and every `require()` of a document returns the same object.
  Destructuring the exports of a module supports plain and renamed properties, plus nested patterns for builtin sub-modules such as `util.types`.
  Computed keys work when they fold to a constant, such as a string literal or a `const` binding.
  A computed key whose value is only known at run time is unsupported.
  Any pattern works on a JSON document.
  Defaults, rest elements, and nested patterns over other modules are unsupported.
  A require cycle compiles with Node.js's partial exports: a module that requires into the cycle reads the exports object as it stands, so a member assigned after the `require` reads `undefined` and the miss reports Node.js's circular-dependency warning.
  Requiring an ES module that is still evaluating throws `ERR_REQUIRE_CYCLE_MODULE` at the call.
  Top-level code that reaches another member of the cycle only through a call or an escaping value is rejected with `SC1016`.
  A top-level `return` ends the module's evaluation.
  It is unsupported when the module assigns exports after it, or when a function that exists before it runs reads a binding declared after it, such as a callback created above the `return` or a function declaration.
