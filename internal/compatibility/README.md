# Node compatibility ledger

This workspace package owns scriptc's Node.js parity system.

- `node-v24.json` pins the Node release tag, commit, and canonical docs/source inputs.
- `static-support.json` overlays dedicated compiler paths and their internal test evidence on the compiler's generated surface manifest.
- `generated/node-v24-internal.json` is the engineering ledger, including implementation evidence and repository test paths.
- `pnpm node-compat:backlog` derives the internal tier-specific work queue from the ledger; it is not committed. It separates verification, implementation, explicit-refusal replacement, and partial-surface audit work, and prioritizes stable Node APIs above experimental, deprecated, and legacy APIs. `island-served` rows are not queued: an island build already answers them.
- `docs/src/generated/node-v24-compatibility.json` is the stripped public artifact consumed by the docs website. It contains compiler-relevant runtime APIs, statuses, verification bases, and user-facing details; documentation, metadata, command-line/configuration entries, and rows that are N/A for native execution remain internal.

Statuses are evidence-aware: `supported` and `partial` require test evidence; `island-served` records that an island build answers the API through the Node island and requires differential test evidence too, but it is not native support; `refused` requires an explicit compiler diagnostic or native throwing stub; `not-implemented` is the actionable backlog for an owned API family with no implementation match; `by-design` records an architectural exclusion; `unreviewed` still needs classification; and `not-applicable` is not a runtime API for that execution tier.

A `features` entry in `static-support.json` names its rows by `chapter`, an optional `parent` heading, and `symbols` or exact `signatures`. A `not-implemented` entry that names evidence is a verified absence: the evidence is the diagnostics program whose snapshot pins the refusal a use of the API gets, and the row's verification basis is `verified-absence` instead of `declared-gap`. Positive claims name differential corpus programs; the `compat-*` programs under `tests/corpus` are grouped by API family for this purpose, and a row they cover stays `partial` because a program proves the call shapes it exercises, not every overload. A member can work from a JavaScript source and be refused from TypeScript, because the bundled declarations list only what the typed lowering compiles; a `compat-*.mjs` program is the evidence for such a row, and the public detail of a row whose only evidence is `compat-*.mjs` programs says the member was exercised from a JavaScript module. Where a typed source reaches the member too, the row also names the program's `compat-*.ts` twin, and its public detail says both sources exercised it; a twin's header lists what it leaves to the JavaScript program. A JavaScript source defers a refusal to a catchable run-time error, so before a row is declared a verified absence its use is also probed from a JavaScript source. A `features` entry may carry a `reason`, one sentence saying why its rows have that status; the generator does not read it, and it is there for whoever reads the manifest or takes a row off the backlog. The `errors` chapter uses it for the codes a compiled binary never raises: codes of a `by-design` chapter (`vm`, `inspector`, V8's own limits) are `by-design`, and the entry names that chapter as its `policy`, since a `by-design` claim rests on a chapter policy; codes the pinned Node documents and raises nowhere in `lib/` or `src/` and codes of the node executable itself (start-up options, snapshots, the debugger) are `not-applicable`, and codes of members that are refused or missing are `not-implemented`. A prose heading that Node's documentation writes with a code span ("Usage with `async/await`") is declared `not-applicable` by a `features` entry, and a module the compiler refuses by name for an architectural reason (`inspector`, `domain`) is a `by-design` chapter policy.

Node documents its globals twice, in the globals chapter and in the chapter of the module that owns them. The generator refuses a snapshot in which a direct row of the globals chapter and the same-symbol row of another chapter (a direct row, or a class row at any depth, since a chapter may nest its classes under a heading) disagree as claimed against unmatched; map both rows, or classify the difference explicitly. A global class binding and the objects of that class are different claims: the `globals` rows for `PerformanceEntry`, `PerformanceMark` and `PerformanceMeasure` are verified absences (a read of the global is refused) while the `perf_hooks` rows for the entries `performance.mark()` and `performance.measure()` return are test-backed.

Run `pnpm node-compat:backlog` from the repository root for a summary. The filters `--tier`, `--action`, `--priority`, `--chapter`, and `--status` compose; use `--format=json` or `--format=tsv` for tooling.

Run `pnpm node-compat` from the repository root after changing the Node pin or the support manifest. `pnpm node-compat --local` does the same without network access while the pin is unchanged, by reclassifying the committed ledger rows; after a merge, `node scripts/regen-generated.mjs` regenerates every generated file instead of a hand merge. `pnpm node-compat:check` is the offline drift/evidence gate; `pnpm --filter @internal/compatibility check:upstream` additionally verifies the pinned upstream inputs over the network.

## npm packages that compile as builtins

The ledger counts Node APIs, so npm packages that compile as a Node builtin have no rows. `packages/compiler/src/frontend/builtin-package-aliases.ts` lists them, each with the checked major versions and the reason its module is that builtin on Node 24. One entry is a documented divergence rather than an identity: `readable-stream` 2.x, 3.x and 4.x compile as `node:stream`; for 2.x and 4.x that is the package's `READABLE_STREAM=disable` behavior. Without that variable Node runs the package's own JavaScript streams. The `tests/corpus/readable-stream-disable` program pins the disabled behavior. 3.x, a copy of Node 10's streams, cannot run disabled on Node 24 (its disable branch throws), so `tests/corpus/readable-stream-3` pins only behavior its own streams share with the builtin.
